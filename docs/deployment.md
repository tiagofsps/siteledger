# Render Deployment

This document describes the Render deployment of the SiteLedger Operations Management application.

The current environment is a **free evaluation deployment**. It is suitable for trying the application, not for real company data. See [Free instance limitations](#free-instance-limitations) and [Upgrade to paid](#upgrade-to-paid).

## Current configuration

- Render Hobby workspace.
- Web service: free instance.
- PostgreSQL: free instance.
- Region: Frankfurt for both.
- PostgreSQL 17, matching the CI service container.
- Production Python: `3.14.10`, because Django 5.2 officially supports up to Python 3.14.
- Local development remains on Python 3.15.2.

SQLite is not used in production: Render's filesystem is ephemeral, and the application relies on `select_for_update()` row locking, which SQLite does not provide.

## Free instance limitations

| Limitation | Effect |
| --- | --- |
| Sleeps after 15 minutes without traffic | the first request takes roughly 30 to 60 seconds |
| 0.1 CPU / 512 MB | adequate for a handful of users, with slow cold starts |
| No `preDeployCommand` | migrations run in the build command |
| No zero-downtime deploys | a brief error while the instance restarts |
| Free PostgreSQL expires after 30 days | the database and all data are deleted |
| No PostgreSQL backups | recovery is only possible from a manual dump |
| 750 free instance hours per month | one always-on service already uses most of them |

Treat this deployment as a test. Do not enter real company data until the database is upgraded to a paid plan.

## How a deploy happens

```text
push to main
  → GitHub Actions test job
  → GitHub checks pass
  → Render build (install, collectstatic, migrate)
  → health check on /login/
  → live
```

`render.yaml` sets `autoDeployTrigger: "checksPass"`, so Render deploys a commit only after its GitHub checks pass. A failing CI run never reaches the deployment. Because Render owns this step, there is no deploy hook and no GitHub secret to manage.

Changes to `render.yaml` itself are not deployed automatically: sync the Blueprint in the Render Dashboard. To redeploy the current commit without pushing, use the service's **Manual Deploy** button.

## Added files

- `render.yaml`: Blueprint for the web service and PostgreSQL database.
- `.github/workflows/ci.yml`: PostgreSQL test workflow.
- Production dependencies in `requirements.txt`:
  - `gunicorn`
  - `whitenoise`
  - `dj-database-url`

## Application settings

`config/settings.py` supports:

- `DATABASE_URL` for Render PostgreSQL, overriding `DJANGO_DB_ENGINE` and the `DB_*` variables
- `RENDER_EXTERNAL_HOSTNAME` automatically added to `ALLOWED_HOSTS`
- `https://<RENDER_EXTERNAL_HOSTNAME>` automatically added to `CSRF_TRUSTED_ORIGINS`
- WhiteNoise static file serving, enabled only when `DJANGO_DEBUG=False`
- compressed manifest static storage, enabled only when `DJANGO_DEBUG=False`

Render sets `RENDER_EXTERNAL_HOSTNAME` automatically.

The Blueprint configures:

- `PYTHON_VERSION=3.14.10`
- `DJANGO_DEBUG=False`
- `DJANGO_TRUST_X_FORWARDED_PROTO=True`
- `DJANGO_SECRET_KEY` generated by Render
- `DATABASE_URL` taken from the Render PostgreSQL database

`DJANGO_ALLOWED_HOSTS` and `DJANGO_CSRF_TRUSTED_ORIGINS` are not set because `RENDER_EXTERNAL_HOSTNAME` covers the default `onrender.com` hostname. Add them only for a custom domain.

The production security defaults remain active when `DJANGO_DEBUG=False`:

- HTTPS redirect
- secure session cookie
- secure CSRF cookie
- HSTS

## First deployment

1. In Render, choose **New → Blueprint** and connect the repository.
2. Select the `main` branch and confirm the Blueprint name.
3. Apply the Blueprint. Render creates the free PostgreSQL database first, then the web service.
4. Wait for the build, the migrations and the health check.
5. Open `https://<service-name>.onrender.com/login/`.

Only paid resources require a payment method; the first deploy itself is free.

## Create the first user

Open the Render Shell for the web service and run:

```bash
python manage.py createsuperuser
```

Create the remaining users through Django Admin at `/admin/auth/user/`.

Do not run `seed_demo` in production.

## Verification

After deployment:

- open `/login/`
- confirm the CSS, JavaScript and HTMX assets load
- log in as the superuser
- verify `/admin/`
- create or verify a project, supplier, article, purchase and movement
- confirm the help page at `/ajuda/`
- confirm the health check path `/login/` is reachable

## Continuous integration

`.github/workflows/ci.yml` runs on every pull request, every push to `main` and on manual dispatch:

1. check out the repository;
2. install Python 3.14.10 and the pinned requirements;
3. run `python manage.py check`;
4. run `python manage.py makemigrations --check --dry-run`;
5. run `python manage.py test` against a PostgreSQL 17 service container;
6. run `python manage.py check` with `DJANGO_DEBUG=False` to validate production settings;
7. run `python manage.py collectstatic --noinput` with `DJANGO_DEBUG=False`, which exercises the WhiteNoise manifest storage.

Tests run with `DJANGO_DEBUG` enabled, as in local development. Running the suite with production settings is not supported: HTTPS redirects change every test response to `301`, and hashed manifest static files break template assertions. Production settings are validated by the last two steps instead.

Running the suite on PostgreSQL matters: the first CI run caught a `FOR UPDATE cannot be applied to the nullable side of an outer join` error that SQLite silently accepted.

## Rollback

Render keeps previous deploys and can roll back the running instance from the Dashboard. Migrations are forward-only, so a rollback that depends on a reverted migration requires a database restore.

## Data safety on the free database

A free PostgreSQL database is deleted 30 days after creation, together with all data, and has no automated backups. Take a dump before the expiry or before any risky change.

The connection string is under the database's **Connect** section, as the external database URL:

```bash
pg_dump --no-owner --no-acl "$EXTERNAL_DATABASE_URL" > ~/backups/siteledger-$(date +%F).sql
```

Restore it into another database with:

```bash
psql "$DATABASE_URL" < ~/backups/siteledger-2026-11-06.sql
```

Keep dumps outside the repository; they contain personal data.

## Upgrade to paid

Upgrading is a Blueprint change plus a sync. The database plan changes in place and keeps its data, so do it before the 30-day expiry if the data matters.

```yaml
databases:
  - name: siteledger-db
    plan: 0.1c-256mb        # was: free

services:
  - type: web
    name: siteledger
    plan: 0.5c-512mb        # was: free
    buildCommand: pip install -r requirements.txt && python manage.py collectstatic --noinput
    preDeployCommand: python manage.py migrate
    startCommand: gunicorn config.wsgi:application --bind 0.0.0.0:$PORT --workers 2 --threads 4 --timeout 60
```

Paid instances support `preDeployCommand`, so migrations move out of the build command and run once per deploy instead of during the build. Enable PostgreSQL backups at the same time. Expected cost is about $13 per month for both resources.

## Media and uploads

No document uploads exist yet. Do not store future invoice or receipt files on Render's local filesystem.

When uploads are introduced, use private object storage such as S3 or Cloudflare R2 and serve files through authenticated views or signed URLs.

## Required manual actions

- Apply the Blueprint and confirm the first deploy.
- Confirm the CI run that precedes it is green.
- Create the superuser through the Render Shell.
- Create the remaining users through Django Admin.
- Take a database dump, or upgrade the database plan before the 30-day free expiry.
- Configure a custom domain and its additional host/CSRF environment variables if needed.
- Confirm Python 3.14.10 as the production runtime, or decide to use Docker with Python 3.15.2.
