# Render Deployment

This document describes the production deployment prepared for Render.

## Assumptions

- Render Hobby workspace.
- Small paid compute plans:
  - web service: `0.5c-512mb`
  - PostgreSQL: `0.1c-256mb`
- PostgreSQL 17, matching the CI service container.
- Production Python: `3.14.10`, because Django 5.2 officially supports up to Python 3.14.
- Local development remains on Python 3.15.2.

Free Render compute is suitable only for temporary testing. Free web services spin down and free PostgreSQL databases expire after 30 days.

SQLite is not used in production: Render's filesystem is ephemeral, and the application relies on `select_for_update()` row locking, which SQLite does not provide.

## Added files

- `render.yaml`: Render Blueprint for the web service and PostgreSQL database.
- `.github/workflows/ci.yml`: PostgreSQL test workflow and Render deploy hook.
- Production dependencies in `requirements.txt`:
  - `gunicorn`
  - `whitenoise`
  - `dj-database-url`

## Application settings

`config/settings.py` now supports:

- `DATABASE_URL` for Render PostgreSQL, overriding `DJANGO_DB_ENGINE` and the `DB_*` variables
- `RENDER_EXTERNAL_HOSTNAME` automatically added to `ALLOWED_HOSTS`
- `https://<RENDER_EXTERNAL_HOSTNAME>` automatically added to `CSRF_TRUSTED_ORIGINS`
- WhiteNoise static file serving, enabled only when `DJANGO_DEBUG=False`
- compressed manifest static storage, enabled only when `DJANGO_DEBUG=False`

Render sets `RENDER_EXTERNAL_HOSTNAME` automatically.

The following environment variables are configured by the Blueprint:

- `PYTHON_VERSION=3.14.10`
- `DJANGO_DEBUG=False`
- `DJANGO_TRUST_X_FORWARDED_PROTO=True`
- `DJANGO_SECRET_KEY` generated by Render
- `DATABASE_URL` taken from the Render PostgreSQL database

`DJANGO_ALLOWED_HOSTS` and `DJANGO_CSRF_TRUSTED_ORIGINS` are not set in the Blueprint because `RENDER_EXTERNAL_HOSTNAME` covers the default `onrender.com` hostname. Add them only for a custom domain.

The existing production security defaults remain active when `DJANGO_DEBUG=False`:

- HTTPS redirect
- secure session cookie
- secure CSRF cookie
- HSTS

## First deployment

1. Push the repository to GitHub.
2. In Render, create a new Blueprint from the repository.
3. Confirm the services and plans in `render.yaml`.
4. Apply the Blueprint.
5. Wait for the first build and deployment.
6. Open the web service’s **Deploy Hook** settings and copy the hook URL.
7. Authenticate GitHub CLI if necessary:

```bash
gh auth login
```

8. Store the Render deploy hook as a GitHub secret:

```bash
gh secret set RENDER_DEPLOY_HOOK_URL
```

9. From now on, pushes to `main` run tests first and trigger Render only if the test job succeeds.

`render.yaml` sets `autoDeployTrigger: "off"`, so Render does not deploy directly on every push. The GitHub Actions deploy job owns deployment. Applying the Blueprint still performs the first deploy; later changes to `render.yaml` require a Blueprint sync in the Render Dashboard.

If `RENDER_DEPLOY_HOOK_URL` is not configured, the deploy job fails intentionally rather than deploying without tests.

## Continuous integration

`.github/workflows/ci.yml` runs on every pull request, every push to `main` and on manual dispatch:

1. check out the repository;
2. install Python 3.14.10 and the pinned requirements;
3. run `python manage.py check`;
4. run `python manage.py makemigrations --check --dry-run`;
5. run `python manage.py test` against a PostgreSQL 17 service container;
6. run `python manage.py check` with `DJANGO_DEBUG=False` to validate production settings;
7. run `python manage.py collectstatic --noinput` with `DJANGO_DEBUG=False`, which exercises the WhiteNoise manifest storage.

Tests run with `DJANGO_DEBUG` enabled, as in local development. Running the suite with production settings is not supported: HTTPS redirects change every test response to `301`, and hashed manifest static files break template assertions. Production settings are validated by the last two steps instead.

The deploy job runs only for `main`, only after the test job succeeds, and calls the Render deploy hook.

## Rollback

Render keeps previous deploys and can roll back the running instance from the Dashboard. Database migrations are forward-only, so a rollback that depends on a reverted migration requires a database restore. Keep Render's automated PostgreSQL backups enabled.

## Create the first user

After the first successful deployment, open the Render Shell for the web service and run:

```bash
python manage.py createsuperuser
```

Create the remaining users through Django Admin at `/admin/auth/user/`.

Do not run `seed_demo` in production.

## Verification

After deployment:

- open `/login/`
- confirm the CSS, JavaScript and HTMX assets load
- log in as the superuser
- verify `/admin/`
- create or verify a project, supplier, article, purchase and movement
- confirm the help page at `/ajuda/`
- confirm static files are served in production
- confirm the health check path `/login/` is reachable

## If using Free compute temporarily

Free compute does not support `preDeployCommand`. If you need a temporary free deployment:

1. Change both plans in `render.yaml` to `free`.
2. Move migrations into the build command:

```yaml
buildCommand: pip install -r requirements.txt && python manage.py collectstatic --noinput && python manage.py migrate
```

3. Remove or disable `preDeployCommand`.
4. Export the database and upgrade before the free PostgreSQL 30-day expiry.

This is not a production configuration.

## Media and uploads

No document uploads exist yet. Do not store future invoice or receipt files on Render’s local filesystem.

When uploads are introduced, use private object storage such as S3 or Cloudflare R2 and serve files through authenticated views or signed URLs.

## Required manual actions

- Approve Python 3.14.10 as the production runtime, or decide to use Docker with Python 3.15.2.
- Push the changes to GitHub.
- Authenticate GitHub CLI with `gh auth login`.
- Create the Render Blueprint from the repository and confirm the plans and region.
- Copy the Render deploy hook URL and set `RENDER_DEPLOY_HOOK_URL` with `gh secret set`.
- Confirm the first CI run and the first Render deploy succeed.
- Create the superuser through the Render Shell.
- Create the remaining users through Django Admin.
- Enable PostgreSQL backups and confirm billing settings.
- Configure a custom domain and its additional host/CSRF environment variables if needed.
